DOCUMENTO 13 — INTEGRACIÓN MCP DE LA CAPA DE PRODUCCIÓN
0. Propósito

Este documento especifica la implementación completa de la superficie MCP de Production Governance, correspondiente al paso 13 del Hito 1.

El objetivo es exponer las capacidades de:

Production Graph.
Decision Memory.
Production Policy Engine.
Production Planner.
Plan validation.
Ejecución segura.
Verificación.
Rollback.
Estado de producción.

a través de una superficie MCP mínima, determinista, segura y de alto nivel.

La implementación debe evitar convertir server.py en un contenedor de lógica de negocio. El servidor MCP debe actuar únicamente como adaptador de transporte y validación de entrada/salida.

La lógica real debe permanecer dentro de:

engine/production/

1. Objetivos obligatorios

La implementación debe cumplir simultáneamente:

Exponer exactamente las herramientas MCP definidas en este documento.
No duplicar lógica de ProductionPlanner, ProductionPolicyEngine, ProductionGraph, DecisionMemory o ProductionExecutor.
Validar todos los argumentos antes de invocar motores internos.
Nunca permitir que una herramienta MCP ejecute una mutación fuera del flujo transaccional existente.
Mantener trazabilidad completa de cada operación.
Devolver errores estructurados y deterministas.
No exponer excepciones internas sin procesar al LLM.
No permitir que el LLM modifique directamente el ProductionGraph.
No permitir que el LLM modifique directamente SessionShadowGraph.
No permitir ejecución automática de memoria histórica.
Mantener compatibilidad completa con las herramientas MCP existentes.
Mantener los tests anteriores 100 % verdes.
2. Principio arquitectónico

La arquitectura final será:

                  MCP CLIENT / LLM
                         │
                         ▼
                ┌─────────────────┐
                │    server.py    │
                │   MCP Adapter   │
                └────────┬────────┘
                         │
                         ▼
                ┌─────────────────┐
                │ Production API  │
                │   Boundary      │
                └────────┬────────┘
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
      Planner         Policies       Executor
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                Production Context
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
       SessionShadowGraph      ProductionGraph
                                    │
                                    ▼
                              DecisionMemory


El LLM nunca debe saltarse la capa de producción.

3. Herramientas MCP definitivas

Se implementarán únicamente estas nueve:

production_status
production_plan
production_validate
production_execute
production_explain
production_history
production_graph
production_rollback
production_memory_search


No crear aliases ni versiones duplicadas.

Por ejemplo, NO crear:

production_create_plan
production_run_plan
production_get_status
production_get_history


La superficie debe permanecer pequeña.

4. Convenciones generales MCP

Todas las herramientas deberán:

recibir argumentos JSON compatibles con FastMCP;
utilizar type hints;
tener docstrings completos;
devolver estructuras serializables;
no devolver objetos Python internos;
no depender de representación textual para transmitir información crítica.

La respuesta debe seguir esta forma conceptual:

{
  "success": true,
  "status": "OK",
  "data": {},
  "errors": [],
  "warnings": [],
  "trace": {
    "request_id": "...",
    "timestamp": "...",
    "engine_version": "..."
  }
}

5. Request ID

Cada llamada MCP debe recibir o generar un:

request_id


Si el cliente no lo proporciona:

request_id = UUID4


Debe almacenarse dentro de la traza de la operación.

Nunca utilizar timestamps como identificadores únicos.

7. production_plan()
7.1 Firma
production_plan(
    intent: str,
    domain: str,
    target: str | None = None,
    profile: str | None = None
) -> dict

7.2 Propósito

Transformar una intención musical en un plan candidato, pero sin ejecutar ningún cambio.

Ejemplo:

"Quiero que el master tenga más volumen"


Nunca debe modificar Live.

8. Validación de intent

intent:

obligatorio;
no vacío;
máximo 2000 caracteres;
debe ser string;
debe eliminar whitespace exterior;
no debe interpretarse como código.

Ejemplos válidos:

"Quiero más claridad en la voz"
"Quiero aumentar el volumen percibido del master"
"Quiero que el bajo tenga más peso"

9. Dominios permitidos

El argumento domain debe utilizar un enum.

Como mínimo:

MUSIC
ARRANGEMENT
SOUND
MIX
MASTER
PERFORMANCE
SESSION


No aceptar valores arbitrarios.

Si se recibe:

"whatever"


la herramienta debe devolver:

INVALID_ARGUMENT


sin invocar el planner.

10. Profile

profile es opcional.

Ejemplos:

EBU_R128
STREAMING
CLUB


Si el dominio no es MASTER, el planner debe decidir si el perfil es relevante.

Nunca asumir silenciosamente que un profile desconocido significa STREAMING.

Importante:

execution_allowed = false

plan_id

18. production_execute()
18.1 Firma
production_execute(
    plan_id: str,
    auto_rollback: bool = True
) -> dict

18.2 Regla crítica

Esta es la única herramienta de las nueve que puede provocar mutaciones en Ableton.

Incluso aquí:

MCP
 ↓
Executor
 ↓
Transaction
 ↓
Ableton


Nunca:

MCP
 ↓
Ableton directamente

19. Precondiciones obligatorias

Antes de ejecutar:

1. Plan existe.
2. Plan está validado.
3. Fingerprint sigue siendo válido.
4. Policy Engine permite ejecución.
5. No existen locks violados.
6. Transaction manager disponible.
7. Ableton disponible.
8. Action list íntegra.
9. Plan no está expirado.


Si cualquiera falla:

NO EXECUTAR

20. auto_rollback

Por defecto:

auto_rollback=True


Si se detecta regresión crítica:

execute
   ↓
verification
   ↓
REGRESSION
   ↓
rollback


Si:

auto_rollback=False


no significa que se pueda ignorar una política crítica.

Significa únicamente que el executor no debe efectuar rollback automático.

La ejecución debe quedar:

EXECUTED_WITH_REGRESSION


o:

RECOVERY_REQUIRED


según la gravedad.

33. production_rollback()
Firma
production_rollback(
    decision_id_or_transaction: str
) -> dict


Debe aceptar:

decision_id


o:

transaction_id


El sistema debe detectar el tipo de identificador.

34. Reglas de rollback

Antes del rollback:

verificar existencia;
verificar reversibilidad;
comprobar estado actual;
comprobar que el rollback sea seguro;
abrir transacción;
ejecutar operaciones inversas;
verificar;
registrar decisión de rollback.
35. Rollback no destructivo

Nunca eliminar:

original decision
original action
original measurement


Se agrega:

ROLLBACK decision


con relación:

original action
      │
      ▼
rollback decision

36. Rollback imposible

Si la acción no es reversible:

{
  "success": false,
  "status": "ROLLBACK_UNAVAILABLE",
  "errors": [
    {
      "code": "NON_REVERSIBLE_ACTION",
      "severity": "CRITICAL"
    }
  ]
}


No intentar una aproximación.

37. production_memory_search()
Firma
production_memory_search(
    query: str,
    context: dict
) -> dict

38. Regla fundamental

La memoria histórica nunca ejecuta acciones.

Su función es únicamente:

retrieve
rank
provide evidence


Nunca:

retrieve → execute

39. Contexto obligatorio

El contexto debe soportar:

{
  "project_id": "...",
  "genre": "...",
  "tempo": 128,
  "key": "F# minor",
  "domain": "MIX",
  "target": "VOCAL",
  "conditions": {}
}


project_id debe ser obligatorio.

Si falta:

INVALID_CONTEXT

40. Ranking de memoria

El ranking debe ser determinista.

Orden recomendado:

1. mismo proyecto
2. mismo dominio
3. mismo target
4. condiciones similares
5. género
6. tempo
7. tonalidad
8. antigüedad


No utilizar random.

{
  "success": true,

  "data": {
    "query": "...",
    "matches": [

Debe ser imposible que el resultado indique:

execute = true

42. Gestión de errores

Todos los errores MCP deben mapearse a códigos estables.

Crear una tabla equivalente a:

Código	Significado
INVALID_ARGUMENT	Argumento inválido
INVALID_DOMAIN	Dominio desconocido
INVALID_PROFILE	Perfil desconocido
PLAN_NOT_FOUND	Plan inexistente
PLAN_EXPIRED	Plan expirado
STALE_PLAN	Fingerprint obsoleto
POLICY_REJECTED	Política rechazó acción
CONFIRMATION_REQUIRED	Requiere confirmación
TRANSACTION_REQUIRED	Falta transacción
TRANSACTION_FAILED	Falló transacción
ABLETON_UNAVAILABLE	Live no disponible
VERIFICATION_FAILED	Falló verificación
REGRESSION_DETECTED	Se detectó regresión
ROLLED_BACK	Se ejecutó rollback
ROLLBACK_UNAVAILABLE	No reversible
GRAPH_INTEGRITY_ERROR	DAG inválido
MEMORY_ERROR	Error de memoria
INTERNAL_ERROR	Error interno
43. Nunca exponer traceback

No devolver:

Traceback...
File "server.py", line 123...


al LLM.

El traceback debe registrarse internamente mediante logging.

La respuesta MCP solamente debe contener:

code
message
severity
request_id

44. Logging

Cada herramienta debe producir logs estructurados:

{
  "request_id": "...",
  "tool": "production_execute",
  "plan_id": "...",
  "decision_id": "...",
  "transaction_id": "...",
  "status": "COMMITTED",
  "duration_ms": 123
}


Nunca registrar:

secretos;
credenciales;
tokens;
información innecesaria del usuario.
45. Idempotencia

production_execute(plan_id) debe proteger contra doble ejecución.

Si el mismo plan ya fue:

COMMITTED


una segunda llamada no debe volver a ejecutar las acciones.

Debe devolver:

ALREADY_EXECUTED


junto con el decision_id original.

Esto es obligatorio para evitar dobles modificaciones si el cliente MCP reintenta una petición.

46. Protección contra ejecución concurrente

No permitir:

execute(plan_A)
execute(plan_A)


simultáneamente.

Debe existir un mecanismo de locking por:

plan_id


y, cuando corresponda, por:

transaction/session

47. Confirmaciones

Una política puede devolver:

REQUIRE_CONFIRMATION


En ese caso:

production_execute()


no debe modificar Live.

Debe devolver:

{
  "success": false,
  "status": "CONFIRMATION_REQUIRED",
  "data": {
    "plan_id": "...",
    "reason": "...",
    "required_confirmation": true
  }
}

48. Regla CRITICAL

Una política:

CRITICAL


nunca puede convertirse en:

WARNING


por parámetros MCP.

No crear:

force=True
ignore_policy=True
unsafe=True


en ninguna herramienta.

La integración MCP debe obtener una única instancia controlada de:

ProductionGraph
DecisionMemory
ProductionPolicyEngine
ProductionPlanner
ProductionExecutor
ProductionContext


No crear una instancia nueva por cada llamada.

De lo contrario se perdería memoria.

4. ProductionGraph
5. DecisionMemory
6. PolicyEngine

Al arrancar nuevamente el servidor:

state/production/


debe cargarse.

Debe recuperarse:

Production Graph.
Decision Memory.
planes pendientes;
decisiones;
versiones;
metadatos.

Las transacciones activas que no puedan verificarse deben marcarse:

RECOVERY_REQUIRED


Nunca asumir automáticamente que fueron exitosas.

import engine.production...
