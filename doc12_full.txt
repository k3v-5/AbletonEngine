DOCUMENTO 12 — ROLLBACK DE PRIMERA CLASE, RECUPERACIÓN Y CONSISTENCIA CAUSAL
0. Propósito

Este documento define la implementación completa del Rollback Engine de PIE.

El objetivo es que cualquier modificación ejecutada por el sistema pueda:

revertirse de forma atómica;
verificarse acústicamente antes y después;
conservar íntegramente su historial;
generar una nueva decisión causal de rollback;
impedir estados parcialmente revertidos;
sobrevivir a fallos de Ableton Live, socket, proceso o validación;
distinguir entre rollback solicitado por el usuario, rollback automático por regresión y rollback por recuperación de transacción incompleta;
mantener sincronizados:
SessionShadowGraph;
ProductionGraph;
DecisionMemory;
estado transaccional;
snapshots;
fingerprint de sesión.

El rollback no debe borrar ni modificar destructivamente el historial anterior.

La regla fundamental es:

Una acción nunca desaparece. Si se revierte, su reversión se convierte en un nuevo hecho causal dentro del Production Graph.

1. Objetivos obligatorios

La implementación deberá garantizar las siguientes propiedades:

Atomicidad

Una operación se revierte completamente o no se revierte.
No puede existir un estado intermedio presentado como válido.

Idempotencia

Solicitar dos veces el mismo rollback no debe ejecutar dos veces la reversión.

Trazabilidad

Toda reversión debe apuntar inequívocamente a la decisión/acción original.

Causalidad

El rollback debe conservar la relación:
INTENT
  ↓
DECISION
  ↓
ACTION
  ↓
RESULT
  ↓
REGRESSION
  ↓
ROLLBACK DECISION
  ↓
ROLLBACK ACTION
  ↓
ROLLBACK RESULT


Verificación

No se considera exitoso un rollback simplemente porque Ableton aceptó los comandos.
Debe existir verificación posterior.

Protección contra rollback incorrecto

Si el estado actual ya cambió de manera incompatible, no se debe aplicar ciegamente el estado anterior.

Persistencia

El historial debe sobrevivir al reinicio del servidor.

Recuperación

Una transacción interrumpida debe poder detectarse y recuperarse.

Determinismo

La misma situación y los mismos datos deben producir la misma decisión de rollback.

No destrucción del historial

Nunca eliminar nodos originales para "volver atrás".

3. Concepto de Rollback

Debe diferenciarse entre:

3.1 Undo

Una operación puramente mecánica:

set_volume(-2 dB)
↓
set_volume(+2 dB)

3.2 Rollback PIE

Una operación causal y verificable:

Decision D1
   ↓
Action A1
   ↓
Result R1
   ↓
Regression detected
   ↓
Rollback Decision D2
   ↓
Rollback Action A2
   ↓
Verification V2
   ↓
Rollback Result R2


Por tanto:

Rollback no es simplemente ejecutar la operación inversa.

Debe reconstruir el estado seguro conocido, verificarlo y documentar el proceso.

8. Identificación del estado objetivo

El rollback debe determinar exactamente a qué estado se quiere regresar.

Debe existir una de estas fuentes:

Prioridad 1

Snapshot transaccional asociado directamente a la acción.

Prioridad 2

Estado inverso registrado en la acción.

Prioridad 3

Snapshot de sesión inmediatamente anterior.

Prioridad 4

Reconstrucción determinista mediante operaciones inversas.

Si ninguna fuente es suficientemente confiable:

ROLLBACK_REJECTED
reason = "NO_SAFE_RESTORE_STATE"


Nunca intentar adivinar.

9. Reversibilidad

Toda acción ejecutable por ProductionExecutor debe declarar:

reversible: bool


y:

rollback_strategy: str


Ejemplos:

SET_VOLUME
→ INVERSE_OPERATION

SET_PAN
→ INVERSE_OPERATION

SET_PARAMETER
→ SNAPSHOT_PARAMETER

CREATE_TRACK
→ DELETE_CREATED_TRACK

DELETE_TRACK
→ SNAPSHOT_RESTORE

CREATE_CLIP
→ DELETE_CREATED_CLIP

DELETE_CLIP
→ SNAPSHOT_RESTORE

DEVICE_PARAMETER_CHANGE
→ PARAMETER_SNAPSHOT

MULTI_OPERATION
→ TRANSACTION_SNAPSHOT

10. Acciones irreversibles

Si una acción es:

reversible = False


deberá bloquearse el rollback automático.

El sistema deberá producir:

REQUIRE_CONFIRMATION


o:

REJECT


según la política.

Nunca deberá afirmar:

rollback successful


si no puede garantizar la reversión.

11. Snapshot obligatorio

Antes de ejecutar cualquier acción modificadora relevante, ProductionExecutor deberá disponer de:

pre_transaction_snapshot


El snapshot debe contener únicamente el estado necesario para recuperar de forma segura, pero deberá ser suficiente para reconstruir las entidades afectadas.

Como mínimo:

{
  "snapshot_id": "...",
  "project_id": "...",
  "session_fingerprint": "...",
  "transaction_id": "...",
  "created_at": "...",
  "tracks": {},
  "devices": {},
  "clips": {},
  "parameters": {},
  "routing": {},
  "mixer": {}
}


No asumir que un snapshot parcial es restaurable.

El snapshot deberá declarar:

completeness: COMPLETE | PARTIAL


Un snapshot PARTIAL no puede utilizarse para rollback automático de objetos que no cubre.

12. Atomicidad

El rollback debe utilizar el mismo sistema transaccional existente.

Nunca ejecutar:

restore volume
restore EQ
restore compressor


como comandos independientes sin transacción.

Debe ser:

BEGIN ROLLBACK TRANSACTION

stage restore volume
stage restore EQ
stage restore compressor

validate

COMMIT

verify


Si falla una operación:

ROLLBACK TRANSACTION


y el estado debe permanecer en el estado previo al intento de rollback.

13. Rollback en dos niveles

Debe existir una distinción explícita entre:

Nivel 1 — Rollback de PIE

Revierte una decisión individual.

Ejemplo:

DECISION: bajar guitarra -2 dB

Nivel 2 — Rollback de transacción

Revierte todo un conjunto atómico.

Ejemplo:

Transaction TX-104
 ├── volume -2 dB
 ├── EQ -1 dB
 └── compressor ratio 2:1


Si las tres operaciones fueron una sola transacción, no permitir rollback parcial salvo que una operación haya sido declarada explícitamente independiente.

14. Dependencias entre decisiones

Antes de revertir una decisión, consultar el Production Graph.

Ejemplo:

D1: crear vocal bus
D2: añadir EQ al vocal bus
D3: añadir compressor al vocal bus
D4: automatizar vocal bus


Si se solicita rollback de D1, D2-D4 pueden depender de D1.

No se debe eliminar D1 dejando referencias inválidas.

El sistema debe responder:

DEPENDENCY_CONFLICT


y listar:

dependent_decisions:
    D2
    D3
    D4


El planificador podrá proponer:

cascade rollback


pero nunca ejecutarlo automáticamente si requiere revertir decisiones posteriores no incluidas en la solicitud original, salvo política explícita.

class RollbackScope(str, Enum):

16. Fingerprint durante rollback

Antes de ejecutar:

fingerprint_current


debe compararse con:

fingerprint_plan


Si no coinciden:

STALE_ROLLBACK_PLAN


Pero debe analizarse si las diferencias afectan al rollback.

Cambio relevante

Ejemplo:

EQ del mismo track cambió.


→ invalidar.

Cambio irrelevante

Ejemplo:

Nombre de un track no relacionado.


→ podría permanecer válido.

La decisión debe utilizar el mismo mecanismo de relevancia de fingerprint definido por el ProductionExecutor.

17. Protección contra sobrescritura

Caso crítico:

D1
↓
usuario modifica manualmente el mismo parámetro
↓
rollback D1


El rollback no debe sobrescribir silenciosamente el cambio manual.

Ejemplo:

D1:
volume = -2 dB

Estado actual:
volume = -5 dB


No ejecutar automáticamente:

volume = 0 dB


porque eso destruiría la modificación posterior.

Debe marcar:

CONFLICTING_STATE


y:

REQUIRE_CONFIRMATION

    relative: float

20. Regresión después del rollback

Un rollback no se considera exitoso simplemente porque restauró valores.

Debe verificarse:

rollback result


Si el estado restaurado produce una nueva regresión crítica:

ROLLBACK_FAILED


El sistema no debe entrar en un ciclo infinito intentando revertir la reversión.

21. Rollback del rollback

No ejecutar automáticamente.

Debe ser tratado como una nueva decisión:

D1 original
D2 rollback D1
D3 rollback D2


Esto permite conservar la causalidad completa.

22. Protección contra ciclos de rollback

Debe existir un límite configurable:

max_automatic_rollback_depth = 1


Para un mismo incidente.

Si:

D1 → rollback → regression → rollback → regression


el sistema debe detenerse y producir:

MANUAL_INTERVENTION_REQUIRED


Nunca continuar indefinidamente.

36. Regla crítica

Una política CRITICAL nunca puede ser ignorada.

Por ejemplo:

ROLLBACK_SNAPSHOT_VALID = CRITICAL


Si falla:

REJECT

37. Idempotencia

Si:

D1


ya fue revertida por:

RB1


y se solicita nuevamente:

rollback(D1)


debe devolver:

ALREADY_REVERTED


No ejecutar comandos nuevamente.

La búsqueda debe utilizar:

target_decision_id


y no solamente rollback_id.

38. No-op

Si la acción ya no tiene efecto en el estado actual:

NO_OP


puede ser válido.

Pero debe registrarse.

Ejemplo:

D1 set volume = -2 dB
actual volume already = 0 dB


Si restaurar a 0 dB no requiere modificación:

ROLLBACK_RESULT = NO_OP


No fingir que se ejecutó una operación.

→ no rollback automático

45. Evitar falsos positivos

El rollback automático debe exigir:

baseline measurement valid
+
post-action measurement valid
+
metric threshold exceeded
+
causal attribution confidence sufficient


Si alguna condición no se cumple:

NO_AUTO_ROLLBACK

46. Confianza

La decisión automática deberá almacenar:

confidence: float


en:

0.0 <= confidence <= 1.0


Nunca permitir valores fuera del rango.

El threshold debe ser configurable.

Por ejemplo:

auto_rollback_confidence_threshold = 0.90


No hardcodearlo en múltiples archivos.

47. Causalidad del rollback

No basta con detectar:

true_peak increased


Debe intentarse establecer:

action
↓
metric changed


Si otra modificación ocurrió simultáneamente:

ACTION A
ACTION B
↓
metric changed


no atribuir automáticamente el problema a A.

Resultado:

CAUSALITY_AMBIGUOUS


y:

REQUIRE_CONFIRMATION

48. Concurrente / carreras

El motor debe asumir que el proyecto puede cambiar mientras se genera o ejecuta un rollback.

Por ello:

plan
↓
fingerprint
↓
validate
↓
execute


debe comprobar nuevamente el fingerprint inmediatamente antes del commit.

No confiar únicamente en la validación inicial.

49. Doble validación

Debe existir:

validation at plan creation


y:

validation immediately before commit


Si cambia el estado entre ambas:

STALE


y cancelar.

50. Integración con locks

Si el objeto objetivo está:

locked = True


el rollback no puede modificarlo.

El sistema debe devolver:

ROLLBACK_BLOCKED_LOCKED_OBJECT


Incluso si el rollback original fue generado por PIE.

El lock tiene prioridad.

51. Seguridad ante snapshots antiguos

Nunca restaurar automáticamente un snapshot excesivamente antiguo sin comprobar:

schema compatibility
session identity
project identity
track identity
device identity
fingerprint lineage


Si el snapshot pertenece a otro proyecto:

REJECT

52. Identidad del proyecto

Todo rollback debe verificar:

request.project_id
snapshot.project_id
context.project_id
transaction.project_id


Todos deben coincidir.

53. Identidad de objetos

No confiar únicamente en nombres.

Incorrecto:

"Lead Vocal"


Correcto:

track_id = stable UUID


Los nombres sirven únicamente como información humana.

54. Objetos eliminados

Si la acción original eliminó una pista:

delete track


el rollback debe poder restaurarla desde snapshot.

Debe comprobar:

track ID;
nombre;
tipo;
routing;
dispositivos;
clips;
mixer state;
sends;
automatización cubierta por snapshot.

Si el snapshot no contiene alguno de esos elementos:

PARTIAL_RESTORE


No declarar éxito total.

55. Objetos creados

Si la acción creó una entidad, rollback deberá eliminarla solamente si:

entity still belongs to source transaction


Si posteriormente fue modificada por otra decisión:

DEPENDENCY_CONFLICT


No eliminarla automáticamente.

56. Operaciones MIDI

Si se modifican notas MIDI:

rollback


debe operar con identificadores estables de eventos cuando existan.

Nunca asumir únicamente:

pitch + start_time


porque pueden existir notas duplicadas.

57. Automatizaciones

Debe conservarse:

target parameter;
lane;
puntos;
tiempos;
valores;
interpolation mode.

El rollback debe restaurar la automatización completa cubierta por la transacción.

58. Dispositivos

Para dispositivos:

device_id
device_type
parameter_id
parameter_value


No identificar dispositivos únicamente por posición:

device_index = 3


porque la cadena puede haber cambiado.

59. Verificación de Ableton

Después del commit:

query actual state


No utilizar exclusivamente la respuesta del comando enviado.

Ejemplo:

set_volume(track, -2)


no equivale a:

volume_confirmed = -2


Debe realizarse lectura posterior.

60. Socket failure

Si falla el socket durante rollback:

ROLLBACK_EXECUTION_INTERRUPTED


No asumir éxito.

El sistema debe entrar en:

RECOVERY_REQUIRED


y posteriormente consultar el estado real de Ableton.

61. Timeout

Todos los comandos deben tener timeout configurable.

Nunca:

while True:
    wait()


Sin límite.

62. Reintentos

Los reintentos deben ser limitados y explícitos.

Por defecto:

max_retries = 1


Una operación no idempotente no debe repetirse automáticamente salvo que el protocolo garantice seguridad.
